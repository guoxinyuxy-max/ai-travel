# AI 旅行拍照助手

上传一张旅行环境照片，AI 分析画面空间结构，给出**可直接照做**的拍摄方案：人物站在哪里、怎么构图、摆什么动作、由同行者或自己怎么拍——并在原图上标注出站位区域与三分参考线。

普通用户面对一个好场景时，最大的障碍不是「不会按快门」，而是不知道**自己该站到哪里**。这个产品把这一步从「凭感觉」变成「照着框站」。

**在线体验：** https://ai-travel-photo.app.workbuddy.host/

---

## 核心链路

```
首页  →  创建拍摄任务  →  AI 分析  →  方案结果  →  提交反馈
        （照片+模式）    （多模态）   （原图标注）   （👍/👎）
```

| 步骤 | 用户做什么 | 产品做什么 |
|---|---|---|
| 1. 首页 | 了解产品、进入 | 展示价值主张与示例效果 |
| 2. 创建任务 | 拍摄或从相册选一张环境照片，选择拍摄方式 | 校验输入，两项齐备才能生成 |
| 3. AI 分析 | 等待（3 步进度提示） | 真实调用多模态大模型理解画面 |
| 4. 方案结果 | 看标注、读建议、决定是否采纳 | 在原图上叠加站位框、三分线、方向箭头 + 四类文案 |
| 5. 反馈 | 👍 有帮助 / 👎 没帮助 | 落库统计 |

另有**异常分支**：当照片不适合分析时（模糊、纯自拍特写、以天空为主等），进入「无法分析」页并给出重拍引导，而不是硬编一套建议。

## 主要功能

- **双入口取图**：移动端直接调起相机，桌面端走文件选择
- **两种拍摄模式**：同行拍摄（由他人掌镜，可变位取景）／自拍模式（设备固定 + 定时），两类模式给拍摄者的指令口吻不同
- **真实多模态分析**：不是模板套话，建议文案会结合画面里实际可见的元素（建筑、水面、街道、树木），构图建议符合照片的实际横竖幅
- **原图标注方案**：站位区域框、三分参考线、拍摄方向箭头，均为百分比坐标，随图片尺寸自适应
- **两道异常防护**：详见下方「关键设计决策」
- **匿名使用统计**：链路漏斗、反馈正负比、重新生成次数，可在数据看板实时查看

## 关键设计决策

### 1. 模型选型：固定 `kimi-k2.5`，而不是让系统自动挑

初版代码取「模型目录里第一个支持图像的模型」，实际命中的是自动路由模型 `auto`——效果不差，但**同一张照片两次结果不一样**，评审现场无法复现，不适合作为演示。

于是做了横向实测：4 张真实公开照片（山湖横幅／海滩横幅／竖幅沙滩／面部特写）× 3 个候选模型，调用参数与生产环境完全一致。结论：

| 模型 | 成功率 | 平均耗时 | 特写判定 | 结论 |
|---|---|---|---|---|
| **kimi-k2.5** | 4/4 | **6.2s**（3.4–7.5s） | 正确识别 | 采用 |
| glm-5v-turbo | 4/4 | 14.8s（有一次 39s） | 正确 | 备选 |
| glm-4.6v | 0/4 | — | — | 平台侧不可用 |

选型约束中还包含一条「发布时间不晚于 2026 年 3 月底」，符合该约束的仅 `kimi-k2.5` 与 `glm-4.6v`。而即使放开这条约束，`kimi-k2.5` 的速度（快一倍以上）、成本（低 37%）与输出质量仍占优，**约束没有带来额外代价**。

代码中保留三级降级：指定模型 → 备选模型 → 目录中第一个支持图像的模型，任一级失效都不会中断流程。
完整实测数据见 [`docs/model-compare.html`](docs/model-compare.html)。

### 2. 异常处理：从「单点防线」改为「两道闸」

初版把是否放行完全押在主模型的自觉上——模型返回 `ok` 就渲染。结果是：一张仰拍天空的照片，模型照常给出建议，**站位框落在了云里**。

修复分三层：

1. **提示词补漏 + 降低随机性**：异常条件明确加入「主体为天空、云层或纯色背景」，并要求模型输出前自检站位是否悬空；`temperature` 由 0.7 降至 0.3
2. **独立二次校验**（核心）：主分析返回 `ok` 后，另发一次轻量模型调用，只问一个问题——这个矩形区域人能不能真实站立。判否即强制转入异常页；校验通道自身故障时放行，避免误伤正常流程
3. **方向校正**：上传压缩时显式按 EXIF 方向重绘，排除手机竖拍时「模型看到的图与用户看到的图方向不一致」的隐患

中途尝试过用**本地像素颜色检测**做第二道闸（零成本），但阈值实测两头都错：蓝天饱和度高被漏判，沙滩的亮色反而被误判为天空——纯颜色特征分不清「天空」与「沙滩／白墙」，方案放弃。

最终 7 个场景实测全通过：3 张真实天空照（蓝天／乌云／积雨云）全部拦截，远山／公路／山湖（站位框压水面属于正常构图）／海滩全部放行。

### 3. 数据分层：先本地跑通，再平滑升级

数据访问统一收在 `src/data/` 一层，页面不直接接触存储：

- `storage.ts` — 访客本机反馈（localStorage）
- `cloud.ts` — 云端连接（数据库 / 模型调用）
- `analytics.ts` — 匿名埋点上报与聚合读取
- `ai.ts` — 分析入口，内部完成「模型调用 → 校验 → 降级」，对页面只暴露一个结果对象

因此把本地能力换成云服务时，UI 层零改动。

## 技术栈

| 层 | 选型 |
|---|---|
| 构建 | Vite 8 |
| 框架 | React 19 + TypeScript 7 |
| 样式 | Tailwind CSS 4（`@theme` 设计 token） |
| 路由 | React Router 7（Hash 模式，静态托管下子路由刷新不 404） |
| 状态 | Zustand |
| 模型与数据库 | WorkBuddy 云服务（免密钥多模态大模型 + 云数据库） |
| 部署 | 静态托管 + CDN |

设计 token 逐项对齐原型稿（黑白极简风），移动优先 + 桌面端两栏布局。

## 数据与隐私

埋点只记录**操作步骤**（进入了哪一步、是否提交反馈），
**不记录照片内容、不记录文字输入、不记录任何可识别个人身份的信息**。
会话标识为随机串存于浏览器 `sessionStorage`，关闭页面即失效。
数据库层已启用行级安全策略：匿名角色只能写入，明细数据不可读，对外仅暴露聚合统计视图。
